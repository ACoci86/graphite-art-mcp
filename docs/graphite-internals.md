# Graphite internals — Phase 0 findings

Verified against upstream `GraphiteEditor/Graphite` at commit
**`ae321b3409113b238f1482a5ad71cbfff6929602`** (2026-09-27).

This document records what the connector relies on inside Graphite, where the
build spec was out of date, and the minimum patch Graphite needs. Anything not
listed here is not assumed by the connector.

---

## 1. Spec paths vs. reality

| Spec path | Status | Notes |
| --- | --- | --- |
| `frontend/wrapper/src/editor_wrapper.rs` | exists, but changed role | Only holds `EditorWrapper`, `create()`, `dispatch()` (**`pub(crate)`**, not callable from JS) and lifecycle hooks. JS-callable commands moved out. |
| `frontend/wrapper/src/editor_commands.rs` | **new** — the real API surface | Every JS-callable command is a plain `fn name(args…) -> Message` inside a `#[editor_commands] mod`. The proc macro generates the `#[wasm_bindgen]` stub (camelCase JS name) and, for the desktop build, an `EditorCommand` enum variant. **This is the file the connector patches.** |
| `frontend/src/messages.ts` | **gone** | Replaced by `frontend/src/subscriptions-router.ts` (typed `subscribeFrontendMessage`) plus generated TS types in `wrapper/pkg/`. |
| `editor/src/messages/portfolio/portfolio_message_handler.rs` | exists | |
| `editor/src/messages/portfolio/document/graph_operation/graph_operation_message.rs` | exists | `NewSvg` signature matches the spec exactly. |
| `editor/src/messages/frontend/frontend_message.rs` | exists | |

Build: the frontend is no longer built with `npm run start`. From the repo root,
`cargo run` builds the Wasm wrapper via `wasm-bindgen-cli`, generates
`frontend/wrapper/pkg/`, and starts Vite in watch mode
(`tools/cargo-run/src/main.rs`). Requirements are checked by that tool
(pinned `wasm-bindgen-cli = 0.2.121`, Node, Rust).

## 2. The `#[editor_commands]` contract (proc-macros/src/editor_commands.rs)

Rules the macro enforces on every command function:

- No visibility modifier, no attributes except `///` docs.
- No `self`, no generics, no `async`, no `unsafe`.
- Parameters must be plain identifiers of types wasm-bindgen can accept
  (`u64` → JS `bigint`, `f64`, `bool`, `String`, `Option<T>`, `Vec<u8>`, tsify types…).
- **Return type is `Message`. Commands cannot return a value to JS.**

Consequence for the connector: any id Graphite would normally allocate
internally must either be **passed in from JS** (for `NodeId`, which is a plain
`u64`) or **observed from the `FrontendMessage` stream** afterwards (for
`DocumentId`, which `NewDocumentWithName` generates itself).

`NodeId(u64)` is generated by a seeded ChaCha20 RNG
(`node-graph/libraries/core-types/src/uuid.rs`); the editor never validates
where a `NodeId` came from, so a JS-generated random 64-bit id is acceptable
(the existing `create_node` command does `NodeId::new()` inside the command
and the `ingest_file` command accepts `insert_parent_id: u64` from JS).

## 3. Dispatch semantics (editor_wrapper.rs `dispatch`)

- `dispatch` calls `editor.handle_message(message)` **synchronously** and then
  invokes the JS callback once per resulting `FrontendMessage`, still inside
  the same JS call. So in the common case, the frontend messages caused by an
  automation command are delivered before the wrapper method returns.
- If the editor mutex is busy (`try_lock` fails, e.g. during node-graph
  evaluation), the message is pushed to `MESSAGE_BUFFER` and flushed on the
  next `requestAnimationFrame` as a `Message::Batched`. The bridge must
  therefore **always wait asynchronously** for the confirming frontend message
  with a timeout rather than assume synchronous delivery.
- After a panic, `EDITOR_HAS_CRASHED` is set and every dispatch is dropped
  silently. `editor.hasCrashed()` is exposed to JS; the bridge checks it before
  every command and reports `GRAPHITE_CRASHED`.

The single entry point for all frontend messages is the callback passed to
`EditorWrapper.create(...)` in `frontend/src/App.svelte`:

```ts
editor = await EditorWrapper.create(operatingSystem(), randomSeed, (messageType, messageData) => {
	subscriptions?.handleFrontendMessage(messageType, messageData);
});
```

`SubscriptionsRouter` stores **one subscriber per message type** in a `Map`,
so the bridge cannot register a second `TriggerSaveFile` listener without
displacing `stores/portfolio.ts`. The bridge instead taps this callback (see §8)
which lets it (a) observe every message and (b) swallow the one export it is
waiting for so no browser download happens.

Messages are serialized with `serialize_large_number_types_as_bigints(true)`:
every `NodeId` / `DocumentId` arrives in JS as a `bigint`. The connector's wire
protocol carries them as **decimal strings**.

## 4. `NewSvg` flow

```
GraphOperationMessage::NewSvg { id: NodeId, svg: String, transform: DAffine2,
                                parent: LayerNodeIdentifier, insert_index: usize, center: bool }
```

Handler (`graph_operation_message_handler.rs` ~L497):

1. `usvg::Tree::from_str(&svg, &usvg::Options::default())`. On failure it emits
   `DialogMessage::DisplayDialogError { title: "SVG parsing failed", .. }` and
   **returns without creating anything** — there is no structured error.
2. If `center`, the placement transform is shifted by the negative visual
   centre of the parsed content, so `(x, y)` becomes the centre of the art.
   Otherwise `(x, y)` is the top-left of the SVG's viewBox.
3. `import_usvg_node(...)` builds a **group layer with node id `id`** and one
   child layer per SVG element (vector paths, text→paths, gradients preserved).
4. `transform_set(placement_transform, TransformIn::Local, false)` on the group.

Existing high-level caller: `DocumentMessage::InsertSvg { name, svg, mouse,
parent_and_insert_index, place_at_origin }` (`document_message_handler.rs`
~L872), reached from `IngestMessage` when a `.svg` file is dropped/pasted.
It does the "right thing" around `NewSvg`:

```rust
let layer_parent = self.new_layer_parent(true);         // needs &self → not reachable from the wrapper
let layer_node_id = NodeId::new();                       // allocated internally → id not observable
responses.add(DocumentMessage::AddTransaction);
new_svg_layer(svg, transform, !place_at_origin, layer_node_id, layer_parent, responses);
// optional SetDisplayName (skip_adding_history_step: true), optional MoveLayerToStack
responses.add(NodeGraphMessage::SelectedNodesSet { nodes: vec![layer.to_node()] });
responses.add(ToolMessage::ActivateTool { tool_type: ToolType::Select });
```

The connector **mirrors this sequence** in a new command but with the id passed
in from JS and the parent defaulting to `LayerNodeIdentifier::ROOT_PARENT`
(`LayerNodeIdentifier::default()`), optionally overridden by a `parent_id`.

`DocumentMessage::AddTransaction` pushes `StartTransaction` + `CommitTransaction`
to the front of the queue; that is how the existing `InsertSvg` handler makes
the whole insertion one undo step, so the same works for us.

SVG validity: because the Rust side only opens a dialog, the bridge
pre-validates the SVG string with the browser's `DOMParser` (`INVALID_SVG`) and
confirms creation by waiting for an `UpdateDocumentLayerStructure` that contains
the requested id (otherwise `LAYER_NOT_CREATED`).

## 5. New document flow

```
PortfolioMessage::NewDocumentWithName { name: String }
```

Handler (`portfolio_message_handler.rs` ~L475): creates a default
`DocumentMessageHandler`, resolves a unique name, generates
`DocumentId(generate_uuid())` internally, loads it, then
`PortfolioMessage::SelectDocument { document_id }`, which results in
`FrontendMessage::UpdateOpenDocumentsList { openDocuments: Vec<DocumentInfo> }`
and `FrontendMessage::UpdateActiveDocument { documentId }`.

`DocumentInfo { id: DocumentId, name: String, path: Option<PathBuf>, is_saved: bool }`.

The wrapper already exposes `renameDocument(newName)`, `selectDocument(id)`,
`closeDocumentWithConfirmation(id)`; there is no existing JS command for
`NewDocumentWithName` (the UI goes through `newDocumentDialog()`), so the
connector adds one. The bridge learns the new `document_id` by waiting for the
next `UpdateActiveDocument` after dispatch.

## 6. Export flow

```
PortfolioMessage::SubmitDocumentExport {
    name: String, file_type: FileType, scale_factor: f64,
    bounds: ExportBounds, artboard_name: Option<String>, artboard_count: usize }
```

- `FileType` (`frontend/utility_types.rs`): `Png | Jpg | Webp | Tiff | Bmp | Tga | Ico | Svg`.
  It is already a proxy type inside the `editor_commands` module.
- `ExportBounds`: `AllArtwork (default) | Selection | Artboard(LayerNodeIdentifier)`.
- The handler calls `executor.submit_document_export(...)`, which evaluates the
  node graph **asynchronously** (result arrives on a later animation-frame poll).
- `NodeGraphExecutor::process_export` (`node_graph_executor.rs` ~L723) then emits:
  - for `Svg`: `FrontendMessage::TriggerSaveFile { name, folder, filters, content: ByteBuf }`
    with the SVG bytes;
  - for raster formats: `FrontendMessage::TriggerExportImage { svg, name, fileType, size }`.
    `stores/portfolio.ts` rasterizes the SVG on a canvas and calls
    `editor.saveRasterizedExport(...)` → `PortfolioMessage::SaveRasterizedExport`
    → the editor encodes it → **another `TriggerSaveFile`** with the image bytes.
- Errors surface as `DialogMessage::DisplayDialogError { title: "Unable to export document" }`
  (e.g. "No bounding box" for an empty document).

**Graphite never writes a file itself on the web build**: the frontend calls
`downloadFile(name, content)`. The bridge intercepts `TriggerSaveFile` while an
export it initiated is pending, forwards the bytes (base64) to the MCP server
over the socket instead of downloading, and the MCP server writes the file.
`TriggerExportImage` is left alone so the existing rasterizer keeps working.

No existing JS command submits an export (the UI uses a Rust-side dialog
layout), so the connector adds `automationExport`.

## 7. Document inspection (for `get_document`, v0.2)

Already streamed to the frontend with no extra work:

- `UpdateDocumentLayerStructure { layerStructure: Vec<LayerStructureEntry> }` —
  tree of `{ layerId, children, childrenPresent, descendantSelected }`
  (children omitted when collapsed in the Layers panel).
- `UpdateDocumentLayerDetails { data: LayerPanelEntry }` per layer —
  `{ id, implementationName, alias, visible, unlocked, selected, childrenAllowed, clipped, … }`.
- `UpdateOpenDocumentsList`, `UpdateActiveDocument`.

The bridge keeps a cache of these and answers `get_document` from it (v0.2).

Other reusable operations for v0.2, all already reachable as JS commands:
`deleteNode(id)`, `setLayerName(id, name)`, `selectLayer(id, ctrl, shift)`,
`deselectAllLayers()`, `moveLayerInTree(parent?, index?)`,
`toggleNodeVisibilityLayerPanel(id)`, `duplicateLayerInTree(...)`.
`GraphOperationMessage::NewArtboard { id, location: DVec2, dimensions: DVec2,
background: Color, clip: bool }` and `NewTextLayer { id, text, font: Font,
typesetting: TypesettingConfig, parent, insert_index }` exist and take
JS-provided ids, so `add_artboard` / `add_text` will follow the same pattern as
`insert_svg`. `FillColorSet` and `TransformSet` exist for `set_fill` /
`set_transform`.

Undo/redo: `DocumentMessage::Undo` / `Redo` exist; not yet exposed as JS
commands (the UI goes through the input mapper), so v0.2 adds two one-liners.

## 8. Minimum Graphite patch

Two files, no new dependencies, no new crates.

### 8.1 `frontend/wrapper/src/editor_commands.rs` (+3 commands, +2 imports)

Inside the existing `#[editor_commands] mod editor_commands` block:

```rust
use editor::messages::frontend::utility_types::ExportBounds;
use editor::messages::tool::utility_types::ToolType;
use graphene_std::vector_types::glam::{DAffine2, DVec2};

/// Automation bridge: create a new document with the given name and make it active.
/// The new `DocumentId` is reported through `FrontendMessage::UpdateActiveDocument`.
fn automation_new_document(name: String) -> Message {
	PortfolioMessage::NewDocumentWithName { name }.into()
}

/// Automation bridge: insert an SVG string as an editable group layer whose node id is `id` (allocated by the caller).
/// `(x, y)` is in the parent's local space (document space for the root). `center` places the art's visual centre at `(x, y)`.
fn automation_insert_svg(id: u64, svg: String, x: f64, y: f64, center: bool, parent_id: Option<u64>, name: Option<String>) -> Message {
	let id = NodeId(id);
	let parent = parent_id.map(NodeId).map(LayerNodeIdentifier::new_unchecked).unwrap_or_default();
	let mut messages: Vec<Message> = vec![
		DocumentMessage::AddTransaction.into(),
		GraphOperationMessage::NewSvg {
			id,
			svg,
			transform: DAffine2::from_translation(DVec2::new(x, y)),
			parent,
			insert_index: 0,
			center,
		}
		.into(),
	];
	if let Some(alias) = name {
		messages.push(
			NodeGraphMessage::SetDisplayName {
				node_id: id,
				network_path: Vec::new(),
				alias,
				skip_adding_history_step: true,
			}
			.into(),
		);
	}
	messages.push(NodeGraphMessage::SelectedNodesSet { nodes: vec![id] }.into());
	messages.push(ToolMessage::ActivateTool { tool_type: ToolType::Select }.into());
	Message::Batched { messages: messages.into() }
}

/// Automation bridge: export the active document. The bytes arrive as `FrontendMessage::TriggerSaveFile`
/// (directly for SVG; after the frontend rasterizes and calls `saveRasterizedExport` for raster formats).
fn automation_export(name: String, file_type: FileType, scale_factor: f64) -> Message {
	PortfolioMessage::SubmitDocumentExport {
		name,
		file_type,
		scale_factor,
		bounds: ExportBounds::AllArtwork,
		artboard_name: None,
		artboard_count: 1,
	}
	.into()
}
```

Generated JS names: `automationNewDocument(name)`,
`automationInsertSvg(id: bigint, svg, x, y, center, parentId?: bigint, name?)`,
`automationExport(name, fileType, scaleFactor)`.

### 8.2 `frontend/src/App.svelte` (+3 lines)

```ts
import { createAutomationBridge } from "/src/automation-bridge";
…
const bridge = createAutomationBridge();
editor = await EditorWrapper.create(operatingSystem(), randomSeed, (messageType, messageData) => {
	if (bridge.intercept(messageType, messageData)) return;   // swallow only the export it is waiting for
	subscriptions?.handleFrontendMessage(messageType, messageData);
});
bridge.attach(editor);
```

plus the new file `frontend/src/automation-bridge.ts` (the bridge itself, ~200
lines, shipped in `graphite-patch/`). The bridge is inert unless the page is
loaded with `?automation=<token>` or `localStorage.graphiteAutomationToken` is
set, so a stock build is unaffected.

## 9. Differences from the build spec — summary

1. `frontend/src/messages.ts` no longer exists; use `subscriptions-router.ts`.
2. JS commands live in `editor_commands.rs` under a proc macro, **not** in
   `editor_wrapper.rs`; `dispatch` is crate-private.
3. Commands cannot return values. `layer_id` is allocated by the bridge and
   passed in; `document_id` is observed from `UpdateActiveDocument`.
4. Export does not take a path. Graphite hands bytes to the frontend; the
   bridge intercepts them and the MCP server writes the file.
5. `graphite_new_document` returns after `UpdateActiveDocument`, not
   synchronously.
6. SVG parse errors are dialog-only in Rust; the bridge validates up front and
   confirms creation via the layer structure.
7. The frontend is built with `cargo run` from the repo root, not `npm start`.

## 10. Upstream changes that would break the connector

Watch these on every re-pin:

- Renaming/removal of `PortfolioMessage::NewDocumentWithName`,
  `GraphOperationMessage::NewSvg`, `PortfolioMessage::SubmitDocumentExport`.
- Changes to `FrontendMessage::UpdateActiveDocument`, `TriggerSaveFile`,
  `UpdateDocumentLayerStructure` field names (they are `serde(rename)`d camelCase).
- Changes to the `#[editor_commands]` macro contract (e.g. if it starts
  rejecting `Option<u64>` or `Message::Batched`).
- The `EditorWrapper.create` callback signature in `App.svelte`.
- `serialize_large_number_types_as_bigints(true)` being turned off (ids would
  become lossy JS numbers).

The connector reports `graphite_commit` from `graphite_get_capabilities` so
mismatches are diagnosable.
